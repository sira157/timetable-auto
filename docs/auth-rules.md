# พรอมต์ระบบล็อกอินและสิทธิ์การใช้งาน: ระบบจัดตารางสอนอัตโนมัติ

สร้างระบบล็อกอินสำหรับเว็บจัดตารางสอน (FastAPI + SQLAlchemy + SQLite ฝั่ง backend, React + TypeScript ฝั่ง frontend) ทุกข้อความที่ผู้ใช้เห็นเป็นภาษาไทย หลักการคือ **ปฏิเสธทุกอย่างที่ไม่ได้อนุญาตไว้อย่างชัดเจน** (deny by default)

## 1. บทบาท (role) 3 แบบ
| role | ชื่อที่แสดง | สิทธิ์ |
|---|---|---|
| `staff` | งานหลักสูตร | ดู/แก้ไขทุกอย่าง รวมถึงจัดการบัญชีผู้ใช้ |
| `teacher` | อาจารย์ | ดูได้เฉพาะตารางสอนของอาจารย์ที่บัญชีนั้นผูกไว้ (`scope_id` = id ของครู) |
| `student` | นักเรียน | ดูได้เฉพาะตารางของกลุ่มเรียน/ห้องเรียนที่บัญชีนั้นผูกไว้ (`scope_id` = id ของกลุ่มเรียน) |

- บัญชี `staff` ต้องไม่มี `scope_id` (เป็น null เสมอ)
- บัญชี `teacher` และ `student` ต้องระบุ `scope_id` ทุกครั้ง

## 2. ฐานข้อมูลและบัญชี
- ตาราง `UserAccount`: `id`, `username` (เก็บตัวพิมพ์เล็กเสมอ, ไม่ซ้ำ), `display_name`, `role`, `scope_id`, `password_hash`, `must_change_password` (boolean), `is_active` (boolean, ค่าเริ่มต้น true), `last_login_at` (UTC)
- **รหัสผ่าน** เก็บด้วย PBKDF2-HMAC-SHA256, 200,000 รอบ, salt 16 ไบต์สุ่ม, รูปแบบ `pbkdf2$<รอบ>$<salt hex>$<hash hex>` ห้ามเก็บรหัสผ่านเป็นข้อความธรรมดา และเทียบด้วย `hmac.compare_digest`
- **ความยาวรหัสผ่านขั้นต่ำ 6 ตัวอักษร** ตรวจทั้งฝั่ง backend และ frontend
- **บัญชีผู้ดูแลเริ่มต้น:** ถ้าฐานข้อมูลยังไม่มีบัญชี `staff` เลย ให้สร้างบัญชี `admin` ชื่อแสดง "งานหลักสูตร" โดยใช้รหัสจากตัวแปรสภาพแวดล้อม `TIMETABLE_ADMIN_PASSWORD` ถ้าไม่ได้ตั้งไว้ใช้รหัส `admin1234` และตั้ง `must_change_password = true` (ใช้ตอนพัฒนาเท่านั้น ต้องตั้งค่า env ก่อนขึ้นระบบจริง)
- ห้ามปิดใช้งานบัญชี `staff` ที่เป็นบัญชีสุดท้าย และห้ามลบบัญชี `staff` ที่เป็นบัญชีสุดท้าย
- ห้ามลบบัญชีที่กำลังใช้งานอยู่ของตัวเอง

## 3. โทเคนและการเข้าสู่ระบบ
- โทเคนเป็นรูปแบบ `<payload base64url>.<ลายเซ็น HMAC-SHA256 hex>`
  - payload ประกอบด้วย `uid`, `exp` (หมดอายุ **12 ชั่วโมง**), และ `pv` (ลายนิ้วมือจาก 16 ตัวท้ายของ `password_hash`)
  - คีย์ลงนาม (`auth_secret`) สุ่ม 32 ไบต์ เก็บในตาราง `app_settings` และสร้างครั้งแรกเมื่อจำเป็น
- **การตรวจโทเคน:** ตรวจลายเซ็นด้วย `compare_digest`, ตรวจวันหมดอายุ, บัญชียังใช้งานอยู่ (`is_active`), และ `pv` ตรงกับรหัสผ่านปัจจุบัน
  - ผลคือ **เมื่อเปลี่ยนหรือรีเซ็ตรหัสผ่าน โทเคนเดิมทุกอันของบัญชีนั้นใช้ไม่ได้ทันที**
- **การล็อกอิน** `POST /api/auth/login` รับ `username`, `password`
  - ตัดช่องว่างและแปลงชื่อเป็นตัวพิมพ์เล็กก่อนค้นหา
  - ตรวจรหัสผ่านเสมอแม้ไม่พบชื่อ (ใช้ hash จำลอง) เพื่อไม่ให้เดาได้ว่าชื่อผู้ใช้มีอยู่หรือไม่
  - ตอบข้อความเดียวกันเสมอเมื่อล็อกอินไม่ผ่าน: "ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง"
  - สำเร็จ: อัปเดต `last_login_at` และคืน `{ token, user }`
- **จำกัดการลองผิด:** นับความพยายามผิดตามคู่ (IP | ชื่อผู้ใช้) ถ้าผิด **5 ครั้งภายใน 5 นาที** ให้ตอบ 429 "ใส่รหัสผิดหลายครั้ง กรุณารอ 5 นาทีแล้วลองใหม่" การนับเก็บในหน่วยความจำ (รีสตาร์ตเซิร์ฟเวอร์แล้วจะเคลียร์)
- `GET /api/auth/me` คืนข้อมูลผู้ใช้ปัจจุบัน
- `POST /api/auth/password` รับ `old_password`, `new_password`
  - ตรวจรหัสเดิมให้ถูก, รหัสใหม่ยาว ≥ 6, รหัสใหม่ต้องไม่ซ้ำรหัสเดิม
  - ตั้ง `must_change_password = false` แล้วคืนโทเคนใหม่ให้ทันที

## 4. ตัวป้องกัน (guard) ทุก API
- ทุกเส้นทางใต้ `/api` ต้องผ่าน guard กลางนี้ ยกเว้น:
  - `POST /api/auth/login` และ `GET /api/health` (สาธารณะ)
  - `GET /api/auth/me` และ `POST /api/auth/password` (ใช้ได้เฉพาะเมื่อล็อกอินแล้ว แม้ยังต้องเปลี่ยนรหัส)
- ส่งโทเคนใน header `Authorization: Bearer <token>`
- ไม่มีโทเคนหรือโทเคนไม่ถูกต้อง → **401** "กรุณาเข้าสู่ระบบ" พร้อม `WWW-Authenticate: Bearer`
- บัญชีที่ `must_change_password = true` → **403** "กรุณาเปลี่ยนรหัสผ่านก่อนใช้งาน" (ใช้ได้เฉพาะ `me` และ `password`)
- บัญชี `staff` ผ่านทุกเส้นทาง
- บัญชี `teacher`/`student` ที่ไม่มี `scope_id` หรือ role ไม่รู้จัก → **403**
- บัญชี `teacher`/`student` ได้สิทธิ์เฉพาะ 3 เส้นทางนี้ และต้องตรงกับบัญชีและตารางที่ใช้งานอยู่:
  1. `GET /api/schedule/active`
  2. `GET /api/schedule/versions/{version_id}/timetable` เมื่อ `version_id` คือเวอร์ชันที่ใช้งานอยู่, `view` ตรงกับบทบาท (`teacher` หรือ `group`), และ `id` = `scope_id` ของบัญชี
  3. `GET /api/reports/{key}` เมื่อ key คือ `teacher_timetables` (ครู) หรือ `group_timetables` (นักเรียน), `id` = `scope_id`, และ `version_id` ว่างหรือเป็นเวอร์ชันที่ใช้งานอยู่
- เส้นทางอื่นทั้งหมดสำหรับบทบาทนี้ → **403** "บัญชีนี้ไม่มีสิทธิ์ใช้งานส่วนนี้"
- ปิด guard ได้ด้วยตัวแปร `TIMETABLE_AUTH_DISABLED=1` **ใช้ในการทดสอบอัตโนมัติเท่านั้น** ห้ามตั้งค่านี้บน Render

## 5. การจัดการบัญชี (เฉพาะ staff)
- `GET /api/auth/users` รายการบัญชี พร้อมชื่อของครู/กลุ่มที่ผูกอยู่ (ถ้าข้อมูลถูกลบหรือนำเข้าใหม่ ให้แสดง "ไม่พบข้อมูล (ถูกลบ/นำเข้าใหม่)" เป็นสีแดง)
- `GET /api/auth/targets?role=teacher|student` รายชื่อครูหรือกลุ่มเรียนให้เลือกผูกบัญชี
- `POST /api/auth/users` สร้างบัญชีเดี่ยว: ชื่อผู้ใช้, รหัสเริ่มต้น (≥ 6), role, scope_id (ถ้าไม่ใช่ staff) เมื่อสร้างแล้วตั้ง `must_change_password = true` ชื่อซ้ำ → 409 "ชื่อผู้ใช้นี้ถูกใช้แล้ว"
- `POST /api/auth/users/bulk` สร้างบัญชีอัตโนมัติให้ครูทุกคนหรือกลุ่มเรียนทุกกลุ่มที่ยังไม่มีบัญชี (ข้ามรายการที่ `is_excluded`)
  - ชื่อผู้ใช้ = รหัสครู/รหัสกลุ่ม (ตัวเล็ก ไม่มีช่องว่าง) ถ้าซ้ำเติม `-2`, `-3`
  - รหัสเริ่มต้นสุ่มจากตัวอักษรที่ไม่คล้ายกัน ความยาว 8 ตัว (`abcdefghjkmnpqrstuvwxyz23456789`)
  - ให้ดาวน์โหลดเป็นไฟล์ CSV (มี BOM UTF-8) ชื่อ "บัญชีผู้ใช้-{role}.csv" ได้ **ครั้งเดียวตอนสร้าง** เพราะรหัสจะไม่แสดงอีก
- `PATCH /api/auth/users/{id}` แก้ได้: รหัสผ่านใหม่ (จะตั้ง `must_change_password = true` ให้เจ้าของเปลี่ยนเองเมื่อเข้าระบบ), ชื่อแสดง, เปิด/ปิดใช้งาน
- `DELETE /api/auth/users/{id}` ลบบัญชี (ตามข้อจำกัดในข้อ 2)
- หน้าบัญชีผู้ใช้แสดงตาราง: ชื่อผู้ใช้, ชื่อแสดง, บทบาท (ป้าย), ผูกกับ (ครู/กลุ่ม หรือ "ทั้งหมด" สำหรับ staff), สถานะ:
  - "ปิดใช้งาน" (เทา มีขีดฆ่า)
  - "ยังไม่เปลี่ยนรหัส" (เหลือง)
  - "ใช้งานอยู่" (เขียว)
- มีป๊อปอัปตั้งรหัสใหม่ให้บัญชี และป๊อปอัปสร้างบัญชีที่เลือกบทบาทและเลือกครูหรือกลุ่มจากรายการ (ปุ่มบันทึกปิดจนกว่าจะกรอกครบ)

## 6. หน้าเข้าสู่ระบบ (Login.tsx)
- พื้นหลังไล่สีจาก indigo-50 ผ่าน white ไป violet-50 การ์ดกลางจอกว้างสูงสุด 384px (max-w-sm) มีเงาอินดิโกบาง
- หัวการ์ด: กล่องไอคอน 44px มุมโค้ง พื้นไล่สี indigo-500 → violet-600 มีอีโมจิ 🗓, ข้อความตัวหนา "ระบบจัดตารางสอนอัตโนมัติ" และหัวรอง "เข้าสู่ระบบ" สีเทา
- ฟอร์ม: ช่อง "ชื่อผู้ใช้" (autofocus, autocomplete `username`) และ "รหัสผ่าน" (type password, autocomplete `current-password`)
- ข้อความผิดพลาดแสดงใต้ฟอร์มเป็นตัวแดง ใช้ `role="alert"`
- ปุ่ม "เข้าสู่ระบบ" เต็มความกว้าง ปิดใช้งานขณะส่งหรือเมื่อยังไม่กรอกชื่อผู้ใช้/รหัสผ่าน ระหว่างส่งข้อความปุ่มเปลี่ยนเป็น "กำลังเข้าสู่ระบบ…"
- ข้อความท้ายฟอร์มสีเทาเล็ก: "นักเรียนและอาจารย์ขอชื่อผู้ใช้/รหัสผ่านจากงานหลักสูตร" (ไม่มีลิงก์สมัครสมาชิก และไม่มีลืมรหัสผ่าน ต้องให้งานหลักสูตรรีเซ็ต)

## 7. หน้าเปลี่ยนรหัสผ่านบังคับ (ChangePasswordPage)
- ใช้การ์ดแบบเดียวกับหน้าล็อกอิน หัวรอง "ตั้งรหัสผ่านใหม่ก่อนใช้งาน"
- ข้อความ: "สวัสดี {ชื่อ} — กรุณาเปลี่ยนรหัสผ่านที่ได้รับเป็นรหัสผ่านของคุณเอง (อย่างน้อย 6 ตัวอักษร)"
- มี 3 ช่อง: รหัสผ่านปัจจุบัน, รหัสผ่านใหม่, รหัสผ่านใหม่อีกครั้ง
- ถ้ารหัสใหม่สองครั้งไม่ตรงกัน แสดง "รหัสผ่านใหม่ไม่ตรงกัน" (ตัวแดง)
- ปุ่ม "เปลี่ยนรหัสผ่าน" (หลัก) และ "ออกจากระบบ" (ghost) อยู่ข้างกัน
- ผู้ใช้เข้าเมนูอื่นไม่ได้จนกว่าจะเปลี่ยนรหัส

## 8. การจัดการสถานะล็อกอินฝั่ง frontend
- โทเคนเก็บใน **sessionStorage** คีย์ `ai-timetable-token` (หายเมื่อปิดแท็บ) ห้ามเก็บใน localStorage
- เมื่อเปิดแอปและมีโทเคน ให้เรียก `/api/auth/me`; ถ้าล้มเหลวให้ออกจากระบบและกลับไปหน้าล็อกอิน
- ทุกคำขอที่ได้ 401 ให้เรียก handler เพื่อออกจากระบบอัตโนมัติ
- ผู้ใช้ที่ `must_change_password = true` จะถูกพาไปหน้าเปลี่ยนรหัสผ่านก่อนเสมอ
- เมื่อเปลี่ยนรหัสสำเร็จ ให้เก็บโทเคนใหม่ที่ backend ส่งกลับมาทันที
- ใช้ React Context (`AuthProvider` / `useAuth`) ให้คอมโพเนนต์เรียก `user`, `loading`, `login`, `changePassword`, `logout`
- แสดงสถานะ `loading` ระหว่างตรวจโทเคนครั้งแรก ไม่แสดงหน้าใดจนกว่าจะรู้ผล

## 9. เมนูผู้ใช้ (UserMenu) บนแถบหัวด้านบนขวา
- แสดง "👤 {ชื่อแสดง} ({ป้ายบทบาท})" (ซ่อนชื่อบนมือถือ, เหลือเฉพาะ)
- ปุ่ม "เปลี่ยนรหัสผ่าน" (บนมือถือเป็นไอคอน 🔑) เปิดโมดัลที่มี 3 ช่องเหมือนหน้าเปลี่ยนรหัส และแสดงข้อความ "เปลี่ยนรหัสผ่านแล้ว" เป็นสีเขียวเมื่อสำเร็จ
- ปุ่ม "ออกจากระบบ" ล้างโทเคนและกลับไปหน้าล็อกอิน

## 10. ข้อกำหนดด้านความปลอดภัยและการใช้งานจริง
- ตั้งค่า `TIMETABLE_ADMIN_PASSWORD` และ `TIMETABLE_DATA_DIR` ใน Render ก่อนเปิดให้ใช้งาน และเปลี่ยนรหัสผ่านผู้ดูแลทันทีหลังล็อกอินครั้งแรก
- อย่าตั้ง `TIMETABLE_AUTH_DISABLED` บนเซิร์ฟเวอร์จริง
- ข้อความผิดพลาดทั้งหมดต้องไม่เปิดเผยว่าชื่อผู้ใช้มีอยู่หรือไม่
- ทุกการสร้าง แก้ไข ลบ บัญชี และการเปลี่ยนรหัสผ่านต้องไม่บันทึกรหัสผ่านลงในประวัติการแก้ไข (ChangeHistory) หรือ log
- ทดสอบอย่างน้อย: ล็อกอินถูกและผิด, ล็อก 429 หลังผิด 5 ครั้ง, โทเคนหมดอายุ, โทเคนเก่าใช้ไม่ได้หลังเปลี่ยนรหัส, บัญชี teacher เข้าตารางของคนอื่นไม่ได้, บัญชี student เข้า API ที่ไม่อนุญาตไม่ได้, บัญชี `must_change_password` ถูกบล็อก, ไม่สามารถปิดหรือลบ staff คนสุดท้ายได้
